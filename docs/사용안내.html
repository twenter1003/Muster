Muster 사용 안내

처음 열었을 때 무엇을 보고 있는지, 어디서부터 눌러야 하는지를 설명합니다. 순서대로 읽으면 15분, 필요한 화면만 찾아 읽어도 됩니다.

무엇을 하는 도구인가

여러 개의 사이드 프로젝트를 동시에 굴리면, 각각이 어디까지 갔는지를 기억하는 일 자체가 일이 됩니다. 어느 프로젝트의 문서가 최신인지, 어떤 개발환경이 승인을 기다리는지, 이번 달 토큰을 얼마나 썼는지가 전부 다른 곳에 흩어져 있습니다.

Muster는 그 흩어진 것들을 프로젝트 단위로 한 화면에 모읍니다. 문서, 개발환경, 에이전트, 로그, 비용, 배포 지표가 한 프로젝트 아래 묶입니다.

중요한 전제가 하나 있습니다. 모든 것의 단위는 프로젝트입니다. 문서도 에이전트도 예산도 프로젝트에 속하고, 당신은 자신이 멤버인 프로젝트만 볼 수 있습니다. 화면이 비어 보인다면 대개 프로젝트가 없거나, 그 프로젝트의 멤버가 아니기 때문입니다.

시작하기

1. 로그인

GitHub 계정 하나로 끝납니다. 별도 회원가입도, 비밀번호도 없습니다. GitHub으로 계속하기를 누르면 GitHub이 권한을 묻고, 승인하면 돌아옵니다.

나갈 때는 상단바 오른쪽의 로그아웃입니다. 누르면 서버의 세션이 그 자리에서 무효가 되고, 화면에 남아 있던 자료도 함께 사라집니다 — 같은 브라우저를 쓰는 다음 사람이 뒤로 가기로 볼 수 없게 하기 위해서입니다.

이때 read:user와 admin:repo_hook 두 가지 권한을 요청합니다. 뒤엣것은 레포를 연동할 때 웹훅을 대신 걸어 주기 위한 것입니다 — 커밋과 배포 결과를 Muster가 자동으로 받아 오는 통로입니다. 레포를 연동하지 않으면 쓰이지 않습니다.

세션은 브라우저가 읽을 수 없는 쿠키에 담기고 서버에 저장됩니다. 로그아웃하면 그 즉시 무효가 됩니다.

2. 첫 프로젝트 만들기

프로젝트 화면의 + 프로젝트 생성으로 만듭니다. 이름만 있으면 됩니다. 만든 사람은 자동으로 owner가 됩니다.

3. 그다음에 할 만한 것

  • 문서 올리기 — PRD·기술명세 같은 것을 프로젝트에 붙여 둡니다.
  • 개발환경 만들기 — 스택을 고르면 Dockerfile과 compose를 만들어 주고, 보안 검사를 통과해야 승인할 수 있습니다.
  • 레포 연동 — 설정 › Git 연동. 배포 성공·실패가 자동으로 쌓이고 DORA 지표가 계산되기 시작합니다.
  • 예산 정하기 — 설정 › 예산. 정해 두면 임계치를 넘을 때 알림에 뜹니다.

환경 구성과 Policy Gate

가장 설명이 필요한 기능입니다. 스택을 말하면 개발환경 설정을 만들어 주고, 보안 검사를 통과해야만 승인할 수 있게 하는 장치입니다.

만드는 법

프로젝트 › 환경 구성 › 새 환경 구성에서 두 가지 방법 중 하나를 씁니다. 폼에서 언어·프레임워크·DB를 고르거나, 자연어로 “Node에 Postgres 붙이고 8000 포트”처럼 적으면 됩니다. 둘을 섞어 써도 됩니다 — 탭을 바꿔도 입력한 값은 사라지지 않습니다.

만든 다음에 벌어지는 일

생성과 동시에 두 가지 검사가 돕니다. trivy는 베이스 이미지의 취약점을, conftest는 규칙 위반(예: 호스트 루트 마운트)을 봅니다. 둘 다 통과해야만 승인 단계로 넘어갑니다.

가장 자주 묻는 것

차단된 구성은 승인으로 풀 수 없습니다. 권한이 있어도, 급해도 마찬가지입니다. 버튼이 숨어 있는 게 아니라 그런 경로 자체를 만들지 않았습니다. 문제를 고쳐서 새 구성을 만드는 것이 유일한 방법입니다.

지나온 길을 볼 수 있습니다

각 구성은 언제 어떤 상태로 옮겨 갔는지, 그리고 누가 그렇게 했는지를 기록합니다. 사람이 한 일(생성·승인·반려·실행)에는 계정 이름이 남고, 검사가 자동으로 판정한 것에는 시스템이라고 적힙니다. 기계가 한 일에 사람 이름을 적으면 “누가 막았나”에 잘못된 답이 남기 때문입니다.

설정 — 프로젝트를 골라서

예산·API 키·Git 연동은 전부 프로젝트 단위라, 화면 위에서 프로젝트를 먼저 고릅니다.

  • 예산 — 토큰·비용 한도와 알림 임계치. 임계치를 넘으면 알림에 뜹니다.
  • API 키 — 에이전트가 쓸 키를 발급합니다. 아래 에이전트 붙이기 참고.
  • Git 연동 — 레포를 연결합니다. 웹훅을 대신 걸어 주고, 그때부터 배포 결과가 자동으로 쌓입니다.
  • 멤버 — 현재 멤버와 역할을 봅니다. 지금은 보기만 됩니다.

읽는 법 네 가지

화면 전체에 일관되게 적용된 규칙입니다. 이것만 알면 나머지는 짐작으로 읽힙니다.

1. 붉은 것은 당신이 처리할 일입니다

신호색은 사람의 처리를 요구하는 것에만 씁니다. 차단된 구성 policy_blocked, 실패한 실행 failed, error 로그, 한도를 넘은 예산, 낮은 헬스 스코어입니다.

승인 대기 policy_passed나 진행 단계 development는 붉지 않습니다. 나쁜 일이 아니라 그냥 상태이기 때문입니다. 훑어봤을 때 붉은 것이 없으면 지금 할 일이 없다는 뜻입니다.

2. —와 0은 다릅니다

0은 재어 본 결과가 0이라는 뜻이고, —는 잴 수 없었다는 뜻입니다. 레포를 연동하지 않은 프로젝트의 헬스 스코어가 —인 것은 점수가 나쁜 게 아니라 계산할 재료가 없다는 뜻입니다. 이 둘을 섞어 쓰지 않습니다.

3. 상태 이름은 원문 그대로 보여 줍니다

policy_blocked, succeeded 같은 값을 한글로 번역하지 않습니다. 이 값들은 API 응답과 로그에도 그대로 나오는 것이라, 번역하면 화면에서 본 것과 로그에서 본 것이 다른 말이 됩니다.

4. 목록은 커서로 넘깁니다

페이지 번호 대신 다음으로 넘깁니다. 보고 있는 사이에 새 항목이 들어와도 같은 항목을 두 번 보거나 건너뛰지 않기 위해서입니다.

에이전트 붙이기

Muster 밖에서 도는 스크립트나 에이전트가 실행 기록과 로그를 밀어 넣을 수 있습니다. 이때는 사람의 로그인이 아니라 프로젝트 API 키를 씁니다.

키 발급

설정 › API 키 › + 키 발급. 용도를 알아볼 이름을 적으면 됩니다.

한 번만 보입니다

발급 직후 화면을 벗어나면 원문 키를 다시 볼 수 없습니다. 서버는 해시만 저장하기 때문에 되찾을 방법이 없고, 재발급만 가능합니다. 그 자리에서 복사해 두세요.

목록에는 muster_••••••••4f2a처럼 마지막 네 자리만 보입니다. 같은 이름의 키가 여럿일 때 어느 것을 폐기할지 고르는 근거입니다.

쓰는 법

헤더에 X-API-Key로 실어 보냅니다.

# 실행 시작을 기록한다
curl -X POST https://<서버>/api/v1/agents/<에이전트 id>/runs \
  -H "X-API-Key: muster_...."

# 로그를 밀어 넣는다 (대시보드에 즉시 흘러갑니다)
curl -X POST https://<서버>/api/v1/projects/<프로젝트 id>/logs \
  -H "X-API-Key: muster_...." \
  -H "Content-Type: application/json" \
  -d '{"level":"info","message":"빌드 시작"}'

키는 발급한 프로젝트 안에서만 통합니다. 다른 프로젝트의 에이전트에 실행을 끼워 넣으려 하면 찾을 수 없다는 응답이 옵니다.

브라우저에서 직접 실행을 시작할 수도 있습니다 — 프로젝트 › 에이전트 탭의 각 행에 있는 실행 버튼입니다.

아직 안 되는 것

쓰다가 “왜 안 되지” 하고 헤매지 않도록, 없는 것을 먼저 적어 둡니다.

없는 것그래서 어떻게 되나
실행 어댑터 환경 구성을 실행하면 running까지 가고 거기서 멈춥니다. 실제로 컨테이너를 띄우는 부분이 아직 없습니다. 상태를 끝내려면 사람이 직접 실행 기록을 닫아야 합니다.
멤버 초대 멤버 목록은 볼 수 있지만 초대·역할 변경·추방이 없습니다. 지금은 한 사람이 자기 프로젝트를 보는 도구입니다.
알림 설정 메일·슬랙으로 내보내는 설정이 없습니다. 알림은 화면에서만 봅니다.
보드에서 끌어 옮기기 진행 단계는 보드에서 카드를 끌어 바꿀 수 없습니다. 보기 전용입니다.

이 목록은 “언젠가 하겠다”가 아니라 지금 상태를 정확히 적은 것입니다. 하나라도 바뀌면 이 문서도 함께 고칩니다.
